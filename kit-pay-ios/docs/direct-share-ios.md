# Encrypted sending from the iOS share sheet

Kit Pay's share extension lets a customer choose a current approved chat, inspect the carried text, edit images or videos, choose PDF pages, and explicitly tap Send. Selecting a system suggestion only preselects a current chat; it never sends automatically. A successful send closes the sheet only after the authenticated backend receipt matches the persisted Signal fanout and attachment commitments. Interrupted or uncertain sends remain saved with Retry and Close. The foreground extension uses an ephemeral session: closing it does not promise an iOS background upload. The main app resumes pending sends after its account, device, privacy and unlock gates pass.

The app and extension use one encrypted canonical messaging store protected by a process lock plus `flock`. Session refresh uses a shared replay nonce and compare-and-swap adoption. The wallet database and its original Keychain access group remain private to the main app. The main app requests its original access group **first**, followed by `$(AppIdentifierPrefix)africa.kit.pay.ios.messaging`; the share extension requests only the messaging group. The broadcast extension does not receive messaging Keychain access. App Store profile preparation and archive verification enforce these boundaries.

For biometric users, destinations remain encrypted when the app's UI locks. The extension requires fresh Face ID or Touch ID against the previously approved biometric domain, with no passcode fallback. Authorization is held only in the current process for five minutes and remains bound to account, session generation, sharing generation and the current denial marker. Privacy/device quarantine and logout create a durable hard denial before Keychain changes. An enrolled-biometric change cannot silently repin the domain. A background restore may republish a biometric-only directory only after all non-biometric gates pass and only with an existing matching pin.

An explicit send journals permanent message/media IDs and attachment keys before work. File encryption is streamed, and verified ciphertext and accepted uploads survive ordinary retries. Fresh server enrollment, capability and roster checks protect initial work and post-upload sealing. Sealing atomically advances the single Signal state and persists exact outgoing request bytes before POST. Timeout, offline, malformed success and lost responses retain those bytes; only authenticated definitive roster or expired-attachment rejection can reopen the required part. No OS lock is held over a network or crypto `await`.

Main-app crypto writes prepare and synchronize one private encrypted journal, publish its opaque transaction ID with canonical messaging state, then rename the prepared file into place. An uncertain shared write retains its journal. Revocation preserves the private receipt until history recovery is finished, and a replacement session cannot seed old private crypto or queued commands into its new generation. Completed media originals are imported into the main app's protected sender cache before the recovery record is consumed. If logout happens before import, confirmed sends retain an encrypted owner-bound display receipt, including downloadable media descriptors; ratchets, wire requests and upload staging are removed. The private history imports that receipt durably before consuming it. Accepted account deletion removes these retained receipts, including retries after session revocation.

Private import also atomically retains the latest 128 encrypted completion receipts in the canonical messaging record. Each contains only the message ID, its generation/account/session binding and a SHA-256 fingerprint of the original destination, text and attachment metadata. Matching retries can recognize a confirmed send after staging and the shared queue entry have been removed, including confirmation that races a failed response or queue update. Every sheet retry checks the original scope and exact input before touching staging or generating attachment keys. Changed content cannot reuse a completed ID. New enqueues still require a current approved destination; completed status survives a later recipient rename or directory removal within the same authorized scope. Logout removes these status receipts with their generation, and decode/save enforce the count, scope, digest and uniqueness limits.

Validation includes native XCTest cases for canonical broker state, biometric and hard-denial fences, concurrent refresh, repeated Keychain failures, uncertain POST replay, wallet/ratchet CAS, and private-journal recovery. The Linux harness executes broker/session logic, private-store recovery and the persisted-request sender retry path with real AES-GCM from swift-crypto, synthetic domain payloads, and injected biometrics/Keychain/network failures. It does not validate Apple's Keychain, LocalAuthentication, UIKit, native libsignal sealing, initial uploads or media receipt semantics. Native compilation and tests remain candidate-publication gates. Physical share-sheet, Face ID and performance checks require the authorized TestFlight candidate and remain required before production rollout or performance claims. Simulator builds explicitly resolve the shared messaging group using the ad-hoc `KITSIM0001.` prefix and verify both built Info.plists against signed entitlements; production keeps Apple's actual signing prefix. Unreferenced private journals retained after uncertain writes currently require conservative housekeeping; they must never be deleted while a shared commit or revocation receipt may reference them.
