# Encrypted sending from the iOS share sheet

Kit Pay's share extension lets a customer choose a current approved chat, inspect the carried text, edit images or videos, choose PDF pages, and explicitly tap Send. Selecting a system suggestion only preselects a current chat; it never sends automatically. A successful send closes the sheet only after the authenticated backend receipt matches the persisted Signal fanout and attachment commitments. Interrupted or uncertain sends remain saved with Retry and Close. The foreground extension uses an ephemeral session: closing it does not promise an iOS background upload. The main app resumes pending sends after its account, device, privacy and unlock gates pass.

The app and extension use one encrypted canonical messaging store protected by a process lock plus `flock`. Session refresh uses a shared replay nonce and compare-and-swap adoption. The wallet database and its original Keychain access group remain private to the main app. The main app requests its original access group **first**, followed by `$(AppIdentifierPrefix)africa.kit.pay.ios.messaging`; the share extension requests only the messaging group. The broadcast extension does not receive messaging Keychain access. App Store profile preparation and archive verification enforce these boundaries.

For biometric users, destinations remain encrypted when the app's UI locks. A dedicated messaging Keychain credential uses `biometryCurrentSet` and `WhenPasscodeSetThisDeviceOnly`. The extension requires fresh Face ID or Touch ID and reads that exact protected credential with the same authenticated context, without passcode fallback. It never receives the wallet's private biometric signing key. Authorization lasts five minutes in the current process only and remains bound to the account, session generation, sharing generation, credential and current denial marker. Privacy/device quarantine and logout create a durable hard denial before Keychain changes. Background restore can republish the encrypted directory after every other gate passes, but cannot create or repair biometric approval.

Build 93 replaces build 92's comparison of opaque LocalAuthentication domain values from different processes. Build 92 also classified unavailable/locked-out biometrics as an enrollment change, and its existing pin could prevent ordinary unlock from repairing sharing. An upgrade requires one fresh biometric unlock in Kit Pay to approve the dedicated credential. Subsequent shares authenticate in the share sheet and need no main-app handoff. Cancellation, unavailable biometrics and a missing/no-longer-usable credential now produce separate, factual errors; a missing item alone does not prove that enrollment changed.

Creation and renewal require a successful main-app private Secure Enclave key operation with the account/session binding captured before authentication. After inserting the candidate credential, the app signs another local challenge with that exact private key and authenticated context, without another prompt, before committing approval. This confirmation is one-use and expires after 60 seconds, including device suspension. It closes an enrollment change between the initial authentication and credential insertion. PIN unlock, ordinary state publication and the share extension cannot renew approval. A noninteractive metadata error cannot trigger replacement. Missing or invalidated private keys preserve the biometric gate. Ordinary publication cannot downgrade the stored requirement; only an explicit verified settings disable or terminal enrollment recovery after a server-verified PIN can clear it. Biometric credential operations occur outside the broker lock; final compare-and-swap checks reject logout, repeated denial, session replacement or concurrent approval. An uncertain authority write retains both the credential and durable denial. A sharing-storage failure leaves sharing closed without undoing successful wallet authentication.

An explicit send journals permanent message/media IDs and attachment keys before work. File encryption is streamed, and verified ciphertext and accepted uploads survive ordinary retries. Fresh server enrollment, capability and roster checks protect initial work and post-upload sealing. Sealing atomically advances the single Signal state and persists exact outgoing request bytes before POST. Timeout, offline, malformed success and lost responses retain those bytes; only authenticated definitive roster or expired-attachment rejection can reopen the required part. No OS lock is held over a network or crypto `await`.

Main-app crypto writes prepare and synchronize one private encrypted journal, publish its opaque transaction ID with canonical messaging state, then rename the prepared file into place. An uncertain shared write retains its journal. Revocation preserves the private receipt until history recovery is finished, and a replacement session cannot seed old private crypto or queued commands into its new generation. Completed media originals are imported into the main app's protected sender cache before the recovery record is consumed. If logout happens before import, confirmed sends retain an encrypted owner-bound display receipt, including downloadable media descriptors; ratchets, wire requests and upload staging are removed. The private history imports that receipt durably before consuming it. Accepted account deletion removes these retained receipts, including retries after session revocation.

Private import also atomically retains the latest 128 encrypted completion receipts in the canonical messaging record. Each contains only the message ID, its generation/account/session binding and a SHA-256 fingerprint of the original destination, text and attachment metadata. Matching retries can recognize a confirmed send after staging and the shared queue entry have been removed, including confirmation that races a failed response or queue update. Every sheet retry checks the original scope and exact input before touching staging or generating attachment keys. Changed content cannot reuse a completed ID. New enqueues still require a current approved destination; completed status survives a later recipient rename or directory removal within the same authorized scope. Logout removes these status receipts with their generation, and decode/save enforce the count, scope, digest and uniqueness limits.

Validation includes native XCTest cases for canonical broker state, biometric credential migration and repair, cancellation, concurrent revocation, session replacement, failed final private-key confirmation, hard-denial fences, concurrent refresh, repeated Keychain failures, uncertain POST replay, wallet/ratchet CAS, and private-journal recovery. The Linux harness runs the broker/session logic using real AES-GCM from swift-crypto and an injected shared credential store. It does not validate Apple's Keychain, LocalAuthentication, UIKit, native libsignal sealing, initial uploads or media receipt semantics. Native compilation and tests remain candidate-publication gates. Physical share-sheet, Face ID and performance checks require the authorized TestFlight candidate and remain required before production rollout or performance claims. Build 92's passing simulator suite did not establish real-device biometric behavior; its user-reported sharing rejection remains a physical regression until retested. Simulator verification checks Xcode's resolved `FAKETEAMID.` identity against both built Info.plists and the simulated entitlements embedded in each arm64 iOS Simulator executable. It requires the app's private group first and messaging group second, with only the messaging group in the share extension. The ordinary ad-hoc signature entitlement dictionary may be empty; signatures are verified separately without changing the products. Production keeps Apple's actual signing prefix and its existing profile and signed-entitlement checks. Unreferenced private journals and Keychain guards retained after uncertain writes require conservative housekeeping; they must never be deleted while an authority, shared commit or revocation receipt may reference them.
